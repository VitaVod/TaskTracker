# Epic 5 Retrospective: Engagement, Recovery, and Notification Experience

Date: 2026-04-30
Epic: Epic 5
Status: Completed Retrospective
Stories: 5 planned, 5 marked done in sprint status

## Scope Reviewed

- Story 5.1: Implement notification preferences domain and API
- Story 5.2: Implement reminder email pipeline for pending tasks
- Story 5.3: Build missed-day recovery experience and guidance
- Story 5.4: Implement progress explanation messages for outcome transparency
- Story 5.5: Integrate transactional notification flows with account events

## Executive Summary

Epic 5 delivered the engagement and notification layer end-to-end: users can configure notification preferences, receive cadence-aware task reminders, recover from missed-day streak breaks with deterministic guidance, and get transparent progress explanations tied to backend rules. Critical account-event notifications were integrated into a monitored delivery pipeline with retry and diagnostics support.

The strongest outcome is consistency of deterministic behavior across backend and frontend surfaces. Preference state, reminder eligibility, recovery prompts, and explanation messages all rely on server-authoritative rules and preserve existing `/api/v1` contract and Problem Details conventions.

The primary concern is operational hardening for growth: reminder and account-event pipelines now exist with retry and logging, but long-run throughput limits, alert thresholds, and runbook maturity should be strengthened before broader scale-up.

## What Went Well

1. Notification preference foundation was delivered with clear defaults and ownership-safe APIs
- Story 5.1 added authenticated read/update endpoints, SQL Server-safe defaults, validation guardrails, and integration tests for persistence, idempotency, and authz boundaries.

2. Reminder pipeline implemented deterministic scheduling and dedupe behavior
- Story 5.2 introduced cadence-window checks, bounded retry semantics for transient failures, run-level logging, and an internal trigger endpoint for controlled execution.

3. Recovery and transparency UX improved user trust
- Stories 5.3 and 5.4 added recovery prompt signals and explanation metadata directly from backend logic, avoiding divergent client heuristics and keeping message behavior deterministic.

4. Transactional account notifications now follow monitored lifecycle states
- Story 5.5 added account-event dispatch lifecycle tracking, idempotent event keys, preference-aware routing, and diagnostics visibility for failed dispatches.

5. Validation signal was strong across API and frontend
- Story artifacts report targeted and full-suite test execution with passing results, including integration tests around retry behavior, recovery mapping, and progress message rendering.

## What Did Not Go Well

1. Epic-level status synchronization remains inconsistent
- All Epic 5 stories are marked done, but `epic-5` remains `in-progress` in sprint status.

2. Operational readiness details are still light in artifacts
- Retry and logging are implemented, but alert thresholds, on-call runbooks, and replay/recovery operator procedures are not documented with the same rigor as code behavior.

3. Story evidence format is still not fully standardized
- Compared with earlier retrospectives, test evidence is improved but still not perfectly uniform in command/result presentation across all stories.

## Key Risks Going Into Epic 6

1. Notification operations risk under incident conditions
- Without explicit runbooks and alert tuning, transient provider outages could generate delayed response and higher support load.

2. Cross-feature regression risk in shared auth/notification infrastructure
- Epic 6 moderation/support capabilities may touch critical account flows; preserving transactional notification behavior and diagnostics coverage is essential.

3. Trust-surface drift risk in progress messaging
- If future changes reintroduce client-side heuristics for outcome explanations, user trust in streak/XP determinism could degrade.

## Lessons Learned

1. Server-authoritative messaging patterns scale better than client-derived interpretation
- Recovery and explanation experiences are more consistent when backend emits explicit reason signals/messages.

2. Delivery reliability should include both retry logic and operator ergonomics
- Implemented lifecycle states and logs are necessary foundations; actionable diagnostics and response playbooks are the next maturity step.

3. Preference-first architecture reduces downstream churn
- Establishing notification preferences in Story 5.1 enabled Stories 5.2 and 5.5 to integrate delivery routing without schema or contract instability.
