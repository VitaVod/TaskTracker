# Epic 2 Retrospective: Task Lifecycle and Deterministic UX Foundation

Date: 2026-04-27
Epic: Epic 2
Status: Completed Retrospective
Stories: 6 planned, 6 marked done in sprint status

## Scope Reviewed

- Story 2.1: Create task domain and API contracts
- Story 2.2: Build task list views for active and completed items
- Story 2.3: Implement task update and organizational attributes
- Story 2.4: Implement task completion toggle with deterministic state
- Story 2.5: Implement task deletion and safe UX confirmation
- Story 2.6: Build task UI states for empty, loading, and error conditions

## Executive Summary

Epic 2 delivered the core task lifecycle foundation and most of the user-facing experience needed for reliable daily task use. The team implemented create, list, update, complete, and delete flows with ownership enforcement, consistent API contracts, and strong accessibility attention.

The most important positive outcome is deterministic behavior across retry and failure paths, including idempotent completion handling and stable RFC 7807 Problem Details contracts with app code and traceId extensions.

The primary concern is implementation evidence consistency. Story 2.6 is marked done but its completion notes indicate drafting and status movement to ready-for-dev, and its file list does not include frontend/backend implementation files. A known flaky concurrent completion-toggle test also remains unresolved.

## What Went Well

1. Strong task domain progression
- Story sequence moved from domain contracts to list UX, update flows, completion semantics, and deletion safety in a logical order.
- Ownership boundaries remained server-authoritative throughout mutation endpoints.

2. Deterministic behavior became a visible standard
- Completion and deletion stories explicitly targeted stable retry outcomes.
- Duplicate-submit prevention and idempotent behavior were treated as first-class concerns.

3. Error contract consistency and observability improved
- Problem Details patterns were reused with stable code and traceId fields.
- This gave frontend error handling predictable mappings across stories.

4. Accessibility and safe UX patterns were maintained
- Confirmation flows, keyboard accessibility, focus behavior, and screen-reader support were repeatedly called out and validated.

## What Did Not Go Well

1. Story 2.6 completion ambiguity
- Story artifact says done, but completion notes describe drafting and ready-for-dev transition.
- Story file list includes only markdown artifacts and no implementation file evidence.

2. Flaky test carried forward
- Story 2.5 notes a pre-existing flaky concurrent completion-toggle test in TasksControllerTests that was not resolved.
- This lowers confidence in deterministic completion behavior under concurrent conditions.

3. Inconsistent evidence depth between stories
- Some stories include explicit implementation and test detail.
- Others provide less concrete validation evidence, reducing traceability confidence.

## Key Risks Going Into Epic 3

1. Progression correctness risk
- Epic 3 depends on completion events and deterministic state transitions. Existing flakiness can affect XP/streak correctness.

2. UX readiness risk
- If Story 2.6 implementation is incomplete, users may face inconsistent empty/loading/error experiences in production paths.

3. Process reliability risk
- If done status is allowed with incomplete implementation evidence, release confidence and handoff quality degrade over time.

## Lessons Learned

1. Definition of Done must include implementation evidence quality
- Status should only become done when file list and completion notes prove delivered code and tests.

2. Deterministic semantics need explicit concurrency stress checks
- Idempotency should be validated under concurrent requests, not only sequential retries.

3. Story-close quality gates need to be uniform
- A lightweight, consistent close checklist would reduce ambiguity and improve auditability.
